مراجعة المشروع الشاملة — تقرير الأخطاء

📘 شرح تفصيلي لكل مشكلة لقتها في مشروع ThreadMarket

الخلاصة الأولانية: المشروع بيبني ويشتغل (TypeScript + Prisma تمام ✅)، لكن في ناسخ من الأخطاء لازم تتصلّح. أشهرها: موديول الـ Category فاضية خالص، وأقسام من الـ Auth مكسورة لأن الـ validators مش متفقين مع الـ controllers.

0. إيه اللي أنا فحصته؟

  1. شغّلت npm run build — تأكد إن الكود بيتجمع من غير أخطاء TypeScript.
  2. شغّلت npx prisma validate — تأكد إن السكيما سليمة.
  3. قريت كل الملفات: auth، user، brand، Category، الـ middleware، والـ utils.
  4. قارنت إيه المطلوب في التاسك وإيه الفعلي في الكود.

1. الوضع الحالي — الشغّال تمام ✅

  • npm run build — يعدي من غير أخطاء.
  • prisma validate — السكيما سليمة، والتعديلات (brandId + imageUrl + العلاقة العكسية) اتحفظت فعلًا في الداتابيز.
  • موديول user (جلب/تعديل البروفايل) — سليم ومنفذ صح.
  • موديول brand (حالة التحقق) — سليم.
  • الـ middleware: authenticate (يقطع التوكن) و authorize (يحدد الأدوار) — سليمين.

3. مشكلة رقم 2 — الـ Auth مكسور 🔴🔴

إيه معنى "الـ validator مش مطابق للـ controller"؟ كل ملف بيشتغل لوحده صح، بس بيتكلموا بأسماء مختلفة لنفس الحاجة. مثلاً:

الـ Endpointالـ validator بيطلب حقلالكود بيقرا حقلالنتيجة
/loginemailidentifierهيقف 401/500 دايماً
/registernameusernameاليوزر هيتعمل بـ undefined
/register-verify-otpemailtokenعمره ما يعدي الـ validation
/reset-passwordemail, otp, passwordtoken, newPasswordعمره ما يعدي الـ validation

ليه ده بيحصل؟

لو فهمت التدفق هيبقى واضح. الزبون بيبعت JSON. الأول بيعدي على validate(schema):

Request Body→validate (بينضف المفتاح المطلوب)→controller (بيقري مفتاح مختلف!)

مثال /login: الزبون بيبعت { "identifier": "a@b.com", "password": "123456" }. الـ schema بيطلب email — مافيش email في الـ body، فالـ validation بيفشل بغلط 400. ولو الزبون بعت email عشان يعدي الـ validation، الـ controller بيدي identifier، فبيبقى undefined، والـ service مش هيقدر يلاقي اليوزر.

4. مشكلة رقم 3 — طول الـ OTP غير متطابق 🔴

الـ OTP بيتم توليده في ملف الـ utils:

// src/shared/utils/otp.ts
const generatedOtp = customAlphabet("0123456789", 5);  // ← 5 أرقام

بس الـ validator بيقول:

otp: z.string().length(6)   // ← 6 أرقام

الفرق بين 5 و6:

  • لو عدّلنا مشكلة رقم 2، الـ OTP اللي هيوصلك في الإيميل (5 أرقام) مش هيقدر يعدي الـ validation لأن بيطلب 6.
  • الـ 5 أرقام اللي بيظهر للإيميل والـ 6 أرقام المطلوب في الـ body — مش هيقبلوا بعض.
الحل: ثبّت الرقم. يا نخلي التوليد 6 أرقام، يا نخلي الـ validation 5. أنضف تعملهم 6 عشان أعلى أمان.

5. مشكلة رقم 4 — وحدات الوقت غلط 🔴

دي مشكلة "ميلي سكوند vs سكوند". الـ JWT بياخد السكوند، وباقي الأدوات بتحسب بالـ ميلي سكوند. الـ .env فيه:

ACCESS_TOKEN_EXPIRY= 86400000        // المقصود: يوم واحد (بالميلي)
REFRESH_TOKEN_EXPIRY = 604800000     // المقصود: أسبوع (بالميلي)

اللي بيحصل فعليًا:

المكانالكودالقيمة الفعليةالصواب
token.service → JWTexpiresIn: 86400000تقريبًا 1000 يوم!86400 ثانية = يوم
الكوكي maxAge604800000 * 1000آلاف الأيام!604800000 ميلي سكوند بس
توكن الـ OTP5 * 60 * 10003.5 أيام بدل 5 دقائق!5 * 60 = 300 ثانية

النتيجة: التوكنات بتفضل "تسامح" فترة طويلة جدًا — ثغرة أمان.

6. مشكلة رقم 5 — اسم الفولدر Category 🟡

الفولدر معمول بحرف كبير:

src/modules/Category/   ← غلط
src/modules/auth/       ← صح
src/modules/brand/      ← صح
src/modules/user/       ← صح

ليه مهم؟ لأن على لينكس و الـ servers (اللي بتعمل deploy عليها) أسماء الملفات case-sensitive. لو كتبت في الاستيراد category.routes والفولدر اسمه Category، هيعملهاش. الأفضل توحيد كل الموديولات بحرف صغير.

7. مشكلة رقم 6 — ملفات dist اتعملها commit 🟡

ملفات البناء dist/ (نتيجة npm run build) متعملة staged في git، وده غلط لأن:

  • مفيش حد محتاج ملفات البناء في الـ repo — هي بتتولّد من الكود.
  • بتعمل تعارضات كثيرة في الـ merge (لأنها بتتغير مع كل build).
  • الحل: إضافة /dist في ملف .gitignore.

8. مشكلة رقم 7 — أمان الـ OTP ⚪

في تدفق الـ sendOtp (نسيان كلمة السر)، الـ OTP بيتخزن plaintext في قاعدة البيانات:

authModel.updateOtp(user.id, generatedOtp, ...)  // النص الصريح!

بينما في تدفق الـ register بيتم hash قبل ما يتحفظ في الـ JWT. لو حد وصل للداتابيز هيعرف كل الـ OTPs. الأفضل يكون hash في الحالتين.

9. ملاحظة صغيرة في الـ validate middleware 🟡

catch (error) {
  if (error instanceof z.ZodError) {
    return next(new AppError(...));
  }
  // لو الخطأ مش Zod → مفيش next() نهائيًا → الطلب "يعلق"
}

لو خطأ من نوع تاني غير الـ Zod، مفيش next() ولا next(error) بيتنادى، فـ الـ request بيقف معلّق. الحل: إضافة return next(error) في الـ catch.
