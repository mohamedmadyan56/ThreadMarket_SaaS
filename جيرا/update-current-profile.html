1. ليه PATCH مش PUT؟

الفرق بيأثر على طريقة كتابة الكود كليًا:

الميثودالمعنىمثال
PUTاستبدال كامل للموارد — لو ما بعتتش حقل، يتصفر/nullارسل {name, email} بس → phone يبقى null
PATCHتحديث جزئي — بيعدّل الحقول المرسلة بس، واللي مسبتهموش بيظلوا زي ما همارسل {name} بس → phone يفضل محفوظ
تأثيرها على الكود: مع PATCH لازم نبني data ديناميكي — نضيف فيه الحقل اللي جاي فقط. لو استخدمنا PUT، كنا هنعمل update بكل الحقول (حتى الفاضية).

2. افهم validate middleware (Zod) — لأن ده أول تاسك فيه Body

المكان: src/shared/middleware/validate.ts. بياخد Zod schema، يدمج الـ body/query/params، ولو البيانات غلط يرمي 400.

export const validate = (schema: z.ZodSchema) => {
  return (req, res, next) => {
    try {
      const data = { ...req.body, ...req.query, ...req.params };
      schema.parse(data);          // لو رمى → نمسك الخطأ
      next();
    } catch (error) {
      if (error instanceof z.ZodError) {
        return next(new AppError(error.issues[0]!.message, 400));
      }
    }
  };
};
قاعدة مهمة للتاسك ده: كل الحقول في Jira اختيارية، لكن المستخدم مفروض يبعت حقل واحد على الأقل. الزود تقدر تعملها بـ .refine() في آخر الـ schema — لو الـ Body فاضي ({}), يرمي 400.

الخطوة 2: user.validators.ts — ملف جديد

schema بيوافق مواصفات Jira بالظبط: كل حقل optional + `.refine` عشان يرفض الـ Body الفاضي.

import z from "zod";

export const updateProfileSchema = z
  .object({
    name: z.string().min(1, "Name cannot be empty").optional(),
    email: z.string().email("Invalid email format").optional(),
    phone: z.string().min(8, "Phone must be at least 8 characters").optional(),
    profilePictureUrl: z.string().url("Invalid URL").optional(),
  })
  .refine((data) => Object.values(data).some((v) => v !== undefined), {
    message: "At least one field must be provided",
  });
إزاي الـ .refine شغال: لو المستخدم بعت {} أو {}، كل القيم هتكون undefined، فـ .some() يرجع false → رمي 400. لو بعت حقل واحد على الأقل، يعدي.

الخطوة 3: user.model.ts — أضيف 3 ميثودز

ميثودز جديدة بنفس نمط findProfileById الموجود:

async findByEmail(email: string) {
  return prisma.user.findFirst({ where: { email } });
}

async findByPhone(phone: string) {
  return prisma.user.findFirst({ where: { phone } });
}

async updateProfile(userId: string, data: any) {
  return prisma.user.update({
    where: { id: userId },
    data,
    select: { id: true, username: true, email: true, phone: true, role: true },
  });
}
ليه الـ select في الـ update برضه؟ عشان الـ update يرجع المستخدم بعد التعديل. لو من غير select هيرجع password و otp — نفس مشكلة الأمان. بناخد الحقول الآمنة بس.

الخطوة 4: user.service.ts — أضيف updateCurrentUser

دي قلب التاسك: فحص الـ uniqueness، بناء الـ data الديناميكي، ثم الـ update.

import { userModel } from "./user.model";
import AppError from "../../shared/errors/AppError";
import { StatusCodes } from "http-status-codes";

class UserService {
  // ... getCurrentUser موجود

  async updateCurrentUser(
    userId: string,
    updates: {
      name?: string;
      email?: string;
      phone?: string;
      profilePictureUrl?: string;
    },
  ) {
    const user = await userModel.findProfileById(userId);
    if (!user) throw new AppError("User not found", StatusCodes.NOT_FOUND);

    const data: any = {};          // ← data ديناميكي (فكرة PATCH)

    if (updates.name !== undefined) {
      data.username = updates.name;          // name ← username
    }

    if (updates.email !== undefined) {
      const exists = await userModel.findByEmail(updates.email);
      if (exists && exists.id !== userId) {
        throw new AppError("Email already in use", StatusCodes.CONFLICT);
      }
      data.email = updates.email;
    }

    if (updates.phone !== undefined) {
      const exists = await userModel.findByPhone(updates.phone);
      if (exists && exists.id !== userId) {
        throw new AppError("Phone already in use", StatusCodes.CONFLICT);
      }
      data.phone = updates.phone;
    }

    if (updates.profilePictureUrl !== undefined) {
      data.picture_url = updates.profilePictureUrl;   // ← mapping
    }

    const updated = await userModel.updateProfile(userId, data);

    return { id: updated.id, name: updated.username };  // ← شكل الرد من Jira
  }
}

export const userService = new UserService();
ليه بنستخدم updates.name !== undefined مش if (updates.name)؟ لأن ممكن المستخدم يبعت "name": "" (فاضي). الـ if (name) هيعدي على الفاضي، لكن !== undefined بيشيك على "الحقل اتضاف في الـ request أو لأ" مش على "فيه قيمة" — وده اللي يفرق في PATCH. لكن لاحظ إن الـ Zod schema بيمنع الفاضي برضه.
ليه فحص الـ uniqueness قبل الـ update؟ جدول الـ DB فيه unique constraint على email و phone. لو حصل تضارب، الـ Prisma هيرمي خطأ 500. بنفحص احنا الأول ونرد رسالة واضحة 409. خد بالك من شرط exists.id !== userId — عشان المستخدم نفسه يقدر يبعت نفس الإيميل بتاعه من غير ما يحصل "تعارض" مع نفسه!

الخطوة 5: user.controller.ts — أضيف handler

import { Request, Response } from "express";
import { userService } from "./user.service";
import { StatusCodes } from "http-status-codes";
import { asyncHandler } from "../../shared/utils/asyncHandler";
import AppError from "../../shared/errors/AppError";

export const updateCurrentUser = asyncHandler(async (req: Request, res: Response) => {
  const userId = (req as any).user?.id;
  if (!userId) throw new AppError("Not authenticated", StatusCodes.UNAUTHORIZED);

  const updated = await userService.updateCurrentUser(userId, req.body);

  res.status(StatusCodes.OK).json({
    success: true,
    message: "Profile updated successfully",
    data: updated,
  });
});

الخطوة 6: user.routes.ts — أضيف الروت

راجع الـ import في أول الملف وضيف الـ schema والـ handler، ثم الروت:

import { Router } from "express";
import authenticate from "../../shared/middleware/authenticate";
import { validate } from "../../shared/middleware/validate";
import { getCurrentUser, updateCurrentUser } from "./user.controller";
import { updateProfileSchema } from "./user.validators";

const router = Router();

router.get("/me", authenticate, getCurrentUser);
router.patch("/me", authenticate, validate(updateProfileSchema), updateCurrentUser);

export default router;
الترتيب هنا مهم جدًا: authenticate الأول (عشان نعرف مين المستخدم) → validate (عشان نتأكد من البيانات) → الـ Controller. لو عكست، حد من غير Token ممكن يبعت بيانات ويعمل update لحساب حد.

8. أخطاء شائعة وقصّها

المشكلةالسبب والحل
الـ password اتعدّل بالغلطمستحيل لو مفيش حقل password في الـ schema والـ service بيبني data من الحقول الـ 4 بس
409 بتيجي على المستخدم نفسهنقص شرط exists.id !== userId في فحص الـ uniqueness
الـ email / phone اتصفّروا لما بعت name بساستخدمت update كامل بدل ديناميكي — ارجع لـ data: any = {} وأنت بتضيف الحقول اللي جاية بس
بيطلع 500 بدل 409نسيت الفحص المسبق وسيبت الـ DB يرمي unique constraint error
Body فاضي عدى من غير خطأنسيت الـ .refine() في الـ schema
update بيرجع password في الردمفيش select في ميثود updateProfile
الخلاصة: التاسك ده بيعلّمك 3 مفاهيم جديدة:
  • PATCH → بناء data ديناميكي يضيف الحقول المرسلة بس.
  • Zod validate → schema بكل الحقول optional + refine لرفض الـ Body الفاضي.
  • Uniqueness check → فحص email/phone قبل الـ update مع استثناء المستخدم نفسه exists.id !== userId.
وشكل الرد النهائي: { id, name } كما طلبت Jira بالظبط.
