شرح قاعدة البيانات و Prisma بالتفصيل

📘 كل اللي حصل معاك في npx prisma migrate dev من الصفر

الخلاصة في سطرين: الـ migrate dev قاللك "هعملك reset وهامسح البيانات" بسبب إن الداتابيز فيها جداول مش مسجلة في التاريخ (مشكلة Drift). الحل الأأمن دلوقتي هو npx prisma db push لأنه بيسوي التغييرات من غير مسح حاجة.

0. إحنا بنتكلم عن إيه أصلاً؟

في المشروع ده عندك ثلاثة أشياء متصلة ببعض:

schema.prisma→Prisma (مترجم)→PostgreSQL (Neon)
  1. schema.prisma — ملف "الرسمة" بتاعة الجداول. هنا بتعرّف الـ models والعلاقات (زي الـ Category اللي عدّلت فيه).
  2. Prisma — أداة بتترجم الرسمة دي لأوامر حقيقية تقدر تتكلم بيها مع قاعدة البيانات.
  3. قاعدة البيانات (Neon) — المكان الفعلي اللي البيانات فيه على الإنترنت. مش في جهازك.

1. إيه الفرق بين الجدول والـ model؟

بساطة: الـ model في السكيما = جدول في قاعدة البيانات. لما تكتب:

model Category {
  id      String @id @default(uuid()) @db.Uuid
  name    String
  brandId String
}

ده معناه: "اعمل جدول اسمه categories، جواه عمود id وعمود name وعمود brandId". التعديل على السكيما مش كفاية — لازم تدخّل "المترجم" عشان يطبق الرسمة على الداتابيز.

2. طريقتين للتطبيق: db push و migrate

Prisma عنده طريقتان عشان يطبق السكيما على قاعدة البيانات، وكل واحد له عقلية مختلفة:

أولاً: prisma db push

العقلية: "من غير أسأل، طبّق السكيما مباشرة."
  • بياخد schema.prisma ويركّبها على الداتابيز على طول.
  • بيضيف ويعدّل الجداول/الأعمدة من غير ما يمسح بيانات موجودة.
  • مش بيسجّل أي تاريخ. يعني مفيش ملفات migration بتتكتب.
  • بيصلح أخطاءك بسرعة في التطوير — لكن مفيش سجل للـ schema على مر الزمن.

ثانياً: prisma migrate

العقلية: "مستني، خلي بالنا. كل تغيير لازم يتوثق ويُسجّل في تاريخ."
  • بيسجّل كل تغيير في ملف migration (ملف SQL بيوصف التغيير) في فولدر prisma/migrations/.
  • بيفضل يتتبع الـ migration history — والـ database ليها _prisma_migrations table بتسجل إيه اللي اتحط وإيه لأ.
  • لو لقي إن الداتابيز مش مطابقة للتاريخ، بيشتبه في حاجة غلط ويطلب منك الـ reset.

3. الـ Migration History — التاريخ

عندك في prisma/migrations/ ملفين بس:

prisma/migrations/
├── 20260724072623_v1/
└── 20260727235013_update_user_model/

يعني التاريخ بيقول: "آخر حاجة أنا أعرفها هي حالة الداتابيز بعد update_user_model". بس الحقيقة إن كل الجداول الباقية (brands, products, Category, orders...) اتضافت بالـ db push من غير تسجيل — فالتاريخ مايعرفش عنها حاجة.

4. الـ Drift — المشكلة اللي ظهرت ليه

لما شغّلت npx prisma migrate dev، Prisma قال لك: "الداتابيز الفعلي فيها جداول (Category, brands, ...) التاريخ بتاعي مش بيقول عليها. في فرق (Drift)."

مهم تفهمه: الـ drift مش خطأ في كودك ولا في السكيما. ده مجرد إن الداتابيز اتبنت بالطريقة اللي "من غير تاريخ" والتاريخ اللي migrate شايفه مش مطابق. هو عايز يصلّح ده — لكن طريقه الوحيد هو إنه يمسح كل حاجة ويعيد البناء من التاريخ.

5. الـ Reset — ليه خطر؟

لما Prisma يقول "We need to reset the public schema... All data will be lost"، ده معناه حرفيًا:

DROP كل الجداول→إعادة بناء من ملفات الـ migrations
  • كل الصفوف اللي في الداتابيز (يوزرز، براندات، منتجات...) هتتمسح.
  • الداتابيز هترجع لشكل الـ migrations بس (اللي هو ناقص — لأن كل الجداول التانية متسجلة في التاريخ أصلًا!).
  • يعني الـ reset مش بس بيمسح بيانات، ده كمان مش هيحل مشكلتك كاملة، لإنه هيبني شكل قديم ويقدر يكمل منها.

6. إزاي المشكلة اللي في كودك اتبنت؟

القصة حصلت كالتالي:

  1. البداية: استخدمت prisma db push مع السكيما القديمة (كان فيه Category قديم من غير brandId).
  2. الداتابيز بقت فيها كل الجداول بس من غير "تاريخ".
  3. إنت عدّلت السكيما — ضفت brandId والعلاقة العكسية.
  4. شغّلت migrate dev (عشان مكتوب في الـ PDF) — فطلع الـ drift وطلب reset.

7. الحل الأأمن — db push

بما إنك مش محتاج تاريخ المايجريشن دلوقتي، الحل البسيط والأأمن:

npx prisma db push     # يطبق التعديلات (brandId + العلاقة) من غير مسح حاجة
npx prisma generate    # يحدّث الـ Prisma Client عشان يتعرف على الحقول الجديدة
  • db push هيضيف عمود brand_id والـ constraints، وهيعدّل الـ index الفريد لـ (brand_id, category_name).
  • البيانات الموجودة هتفضل زي ما هي — لأنه مبيقولش reset.

8. مقارنة سريعة

المعيارprisma db pushprisma migrate
بيمسح بيانات؟لأ — بيضيف ويعدّل فقطبيطلب reset (مسح) لو حصل drift
بيسجّل تاريخ؟لأأيوه — ملفات migration
مناسب ليه؟تطوير سريع ومشروع صغيرمشاريع فيها فرق وبيئة production
بيمسح وقت؟بيتعبك وقت المشاكلبيحفظلك تاريخ التغييرات

9. متى نستخدم migrate صح؟

لو يوم ما حبيت تدخل في عالم الـ migrations صح، الخطوات الصح:

# 1) ساوي السكيما بالواقع الأول
npx prisma db push
# 2) اعمل baseline (بيقول لـ Prisma: "الحالة دي دي المرجع")
npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > prisma/migrations/0000_init.sql
npx prisma migrate resolve --applied 0000_init
# 3) من بعدها اشتغل بـ migrate dev بالعادي
npx prisma migrate dev --name add_brand_relation_to_categories

لكن لحقت دلوقتي: كفاية db push عشان تخلّص التاسك.

10. خلاصة الموقف

شغّل دولتين وخلاص:
npx prisma db push
npx prisma generate

وبعدين ارجع نكمّل في موديول الـ category.
