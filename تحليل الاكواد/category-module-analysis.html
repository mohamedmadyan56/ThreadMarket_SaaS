تحليل Category Module — ThreadMarket SaaS

تحليل شامل لوحدة التصنيفات (Categories) في المشروع: هي إيه؟ بتعمل إيه؟ أجزائها إيه؟ وفيها مشاكل إيه؟

1) إيه هو الـ Category Module؟

الـ Category module هو الجزء المسؤول عن إدارة التصنيفات (Categories) في النظام. التصنيفات هي الطريقة اللي بيها بنقسم المنتجات لمجموعات (مثلاً: ملابس رجالي، نسائي، أطفال، أحذية، إكسسوارات...).

سؤال مهم: إيه علاقته بالـ Brand؟
في المشروع ده، كل براند (Brand) عنده تصنيفاته الخاصة بيه. يعني التصنيفات مش "عامة" على مستوى المنصة كلها، لكن كل براند بيبقى عنده قائمة تصنيفات ليه لوحده — عشان كده الكاتيجوري مرتبطة ببراند معين بـ brandId.

دور الـ module بالظبط دلوقتي (في شكله الحالي) بيتركز في حاجة واحدة:

الوظيفةالحالة دلوقتي
جلب التصنيفات (مع بحث + تقسيم صفحات)✅ موجودة
إنشاء تصنيف جديد❌ غير موجود
تعديل تصنيف❌ غير موجود
حذف تصنيف❌ غير موجود
إخفاء/إظهار تصنيف❌ غير موجود

3) شرح الكود سطر بسطر

أ) الطبقة الأولى: الـ Model — category.model.ts

import prisma from "../../config/database";

class categoryModel {
  async getCategories(filter: {
    search: string;
    skip?: number;
    take?: number;
  }) {
    return await prisma.category.findMany({
      where: {
        name: { contains: filter.search },          // بحث في الاسم
        description: { contains: filter.search },    // بحث في الوصف
      },
      skip: filter.skip,                             // تخطي لصفحات (pagination)
      take: filter.take,                             // عدد النتائج (limit)
    });
  }
}

export const category = new categoryModel();

الوظيفة: ده اللي بيتكلم مع قاعدة البيانات. بيستخدم Prisma ORM عشان يجيب التصنيفات من جدول Category.

  • contains → بحث جزئي (يعني "أحذ" هتطابق "أحذية" و"أحذية رياضية").
  • skip و take → أداة الـ pagination (تقسيم الصفحات): نعدّي عدد معين ونرجع عدد معين.

ب) الطبقة الثانية: الـ Service — category.service.ts

import { category } from "./category.model";

class CategoryService {
  async getCategories(filter: { search: string; skip?: number; take?: number }) {
    return await category.getCategories(filter);
  }
}

export const categoryService = new CategoryService();

الوظيفة: طبقة الـ Business Logic. المفروض هنا كل "القرارات" تتحط (التأكدات، الصلاحيات، القواعد). لكن حاليًا هي مجرد pass-through — بتاخد الفلتر وتمرره للـ model مباشرة من غير أي منطق.

ج) الطبقة الثالثة: الـ Controller — category.controller.ts

export const getCategories = asyncHandler(async (req: Request, res: Response) => {
  // todo => Discuss about category ownership and creation is for admin and for every brand
  const { search, limit = 10, page = 1 } = req.params as { search: string; limit: string; page: string };
  const skip = (Number(page) - 1) * Number(limit);
  const filter = { search, skip, take: Number(limit) };
  const categories = await categoryService.getCategories(filter);
  if (!categories || categories.length === 0) {
    throw new AppError("Categories not found", StatusCodes.NOT_FOUND);
  }
  res.status(StatusCodes.OK).json({
    success: true,
    message: "OK",
    data: { categories, total: categories.length, page: Number(page) },
  });
});

الوظيفة: هو الـ "بوابة" — بيستقبل الطلب من المستخدم، بيحسب الـ skip للـ pagination، بيستدعي الـ service، وبيرد على المستخدم بالـ JSON.

د) الطبقة الرابعة: الـ Routes — category.routes.ts

import { Router } from "express";
import authenticate from "../../shared/middleware/authenticate";
import { authorize } from "../../shared/middleware/authorize";
import { getCategories } from "./category.controller";

const router = Router();

router.use(authenticate);          // أي طلب لازم يكون فيه token أولاً

router.route("/").get(getCategories);   // GET /categories

export default router;

الوظيفة: بيعرّف المسار (endpoint) وبيحدد الـ middlewares اللي بتمشي عليه قبل ما يوصل للـ controller. حاليًا: الـ authenticate بيشتغل على كل الـ routes في الملف (لإنه متحط بـ router.use).

4) إزاي الكود شغال؟ (Request Lifecycle)

لو جيت بنتطلب من الـ API، سلسلة التنفيذ هتكون:

GET /api/v1/categories?search=أحذية&page=1&limit=10
        │
        ▼
[1] authenticate (middleware) ── يتحقق من الـ JWT token ── لا يوجد؟ ──▶ 401 Unauthorized
        │
        ▼
[2] getCategories (controller)
        │  يقرأ الـ params (search, limit, page)
        │  يحسب skip = (page - 1) * limit
        ▼
[3] categoryService.getCategories(filter)
        ▼
[4] category.getCategories(filter)   ← model (Prisma)
        │  SELECT * FROM categories WHERE name LIKE '%أحذية%' LIMIT 10 OFFSET 0
        ▼
[5] يرجع النتيجة → controller
        │  لو فاضية → 404 Categories not found
        ▼
[6] 200 { success: true, message: "OK", data: { categories, total, page } }

5) أهم مشكلة: قراءة من req.params بدل req.query 🔴

الخطأ الأكبر في الـ module: الـ controller بيقرأ بيانات البحث والصفحات من req.params، لكن الحقيقة إن search و limit و page هي Query Parameters (بتيجي بعد علامة ? في الـ URL)، ومش جزء من الـ path. 
الـ URL:  /api/v1/categories?search=أحذية&page=1&limit=10
                              │                        │
                     req.query.search  ← هنا (صح)      │
                     req.params  ← هنا فاضي ❌ (الغلط)

في Express:
  req.query  = { search: "أحذية", page: "1", limit: "10" }   ✅
  req.params = {}                                            ❌

النتيجة:

  • كل القيم هتكون undefined.
  • Number(undefined) = NaN → الـ skip هيبقى NaN → الـ Prisma query هتبوظ.
  • البحث مش هيشتغل أبدًا — لأن filter.search هيبقى undefined.

6) بقية المشاكل المكتشفة

🔴 مشكلة 2: الـ where بينضرب بـ AND بدل OR

where: {
  name:        { contains: filter.search },   // (1)
  description: { contains: filter.search },   // (2)
}

في Prisma، لما تحط أكثر من شرط جوه where بدون OR، بيعتبرهم AND — يعني لازم الكاتيجوري يكون اسمها و وصفها معًا يحتويان كلمة البحث. المفروض ده يبقى OR عشان لو الكلمة ظهرت في الاسم بس أو في الوصف بس، الكاتيجوري تظهر:

where: {
  OR: [
    { name:        { contains: filter.search } },
    { description: { contains: filter.search } },
  ],
}

🔴 مشكلة 3: البحث بيشمل الـ description رغم إنه مش موجود في الموديل

في الـ Prisma schema، الـ Category مالهاش حقل اسمه description (الحقول هي: id, brandId, name, imageUrl, media, ishidden, ...). فأي query بتحاول تستخدم description هتخرب وتعمل خطأ TypeScript / Prisma عند الـ runtime أو الـ compile.

🔴 مشكلة 4: البحث مش insensitive

الـ contains بشكل افتراضي في PostgreSQL حساس لحالة الأحرف (case-sensitive). يعني لو بحثت بـ "shoes" مش هيلاقي "Shoes". المفروض نضيف:

{ contains: filter.search, mode: "insensitive" }

🟡 مشكلة 5: رمي 404 لو مفيش نتائج

لو المستخدم بحث عن حاجة ملهاش نتائج، فده مش خطأ — دي حالة طبيعية. المفروض نرجع 200 بمصفوفة فاضية. الـ 404 مناسبة لما الـ resource نفسه مش موجود (مثلاً كاتيجوري بـ id معين مش موجودة).

🟡 مشكلة 6: total بتحسب عدد نتائج الصفحة مش العدد الكلي

سطر total: categories.length بيديك عدد العناصر اللي رجعت في الصفحة دي (10 مثلاً)، مش العدد الكلي لكل الكاتيجوريات. عشان تعرف العدد الكلي لازم query منفصلة بـ prisma.category.count().

🟡 مشكلة 7: category.validators.ts فارغ

الملف فاضي، لكن الـ validate middleware موجود في المشروع ومستخدم في موديولات تانية. يعني مفيش أي تحقق من المدخلات على الـ endpoint ده — مفيش تأكيد إن page رقم موجب أو إن limit في حدود معينة.

🟡 ملاحظة: الـ brandId مش مفلتر في الـ query

بما إن التصنيفات لكل براند مستقلة، المفروض الـ query يقدر ياخد brandId ويعمل فلترة بيه — عشان البراند يشوف تصنيفاته هو بس. حاليًا بترجع كل تصنيفات النظام.

8) الخلاصة (Summary)

  • ✅ الـ module في شكله الحالي هو قائمة تصنيفات بس (GET مع بحث و pagination) — مفيش Create/Update/Delete.
  • ✅ متبنية على بنية طبقات نظيفة (routes → controller → service → model) بنفس نمط باقي المشروع.
  • ✅ محمية بـ authentication (كل الطلبات محتاجة token).
  • ❌ فيه خطأ جوهري هيخلي الـ endpoint مش شغال أصلاً: القراءة من req.params بدل req.query.
  • ❌ بحث مكسور (AND بدل OR + حقل غير موجود + case-sensitive).
  • ❌ مفيش validation و مفيش فلترة بالبراند و total غلط.
الخطوة الجاية المقترحة: إصلاح المشاكل الـ 8 فوق، وبعدين إضافة الـ CRUD الكامل (Create / Update / Delete) بالتوازي مع التاسكات الموجودين في Jira — وده هيخلي الـ module كامل وجاهز للاستخدام الفعلي من البراندات.
